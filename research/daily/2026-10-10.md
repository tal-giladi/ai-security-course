### C-20261010-01 · MoE router telemetry leaks fine-tuning membership: a router-augmented membership-inference attack raises TPR@1%FPR by 2.7-9.4pp across 9 settings, surviving full-FT/frozen-router/LoRA/instruction-tuning

- **Class:** A
- **Date discovered:** 2026-10-10
- **Date published:** 2026-10-07 (v1)
- **Source:** https://arxiv.org/abs/2610.10616
- **Organization/researchers:** Yixin Tan, Jiayang Liu, Lu Sun, Yuke Hu, Zheng Li, Rui Wen (affiliation not stated on the abstract page; not independently re-verified this run).
- **Category:** extraction/inversion/membership
- **What changed:** Mixture-of-Experts (MoE) is now a mainstream production LLM architecture (Mixtral, DeepSeek-V3, Qwen3-MoE, Llama 4, GPT-OSS and others route tokens to a subset of experts). This paper is the first to show that the router's own telemetry (which experts a token was sent to) is itself a side channel that leaks whether a given example was in the model's fine-tuning set, over and above what output-side signals already reveal — and that this leakage is not an artifact of one training recipe.
- **Technical summary:** The authors build a router-augmented membership-inference attack: a classifier trained on shadow models that combines aggregated routing features with a strong existing output-signal ensemble (rather than relying on either alone). Evaluated across 3 MoE architectures x 3 data domains (9 settings total), the router signal increases true-positive rate at a fixed 1% false-positive rate by 2.7 to 9.4 percentage points over the output-only ensemble, in every one of the 9 settings. The leakage persists across full fine-tuning, frozen-router training, LoRA, and instruction tuning, and remains observable even with only discrete expert-selection labels, restricted telemetry, or a single shadow model. The authors attribute this to fine-tuning writing membership information into hidden representations, which the router's projection exposes even when the router's own parameters are frozen; they also show that perturbing the exposed telemetry reduces the extra leakage only in proportion to how much the telemetry's fidelity is degraded (i.e., there's a utility/leakage trade-off for anyone trying to patch this by noising the router signal).
- **Why it might matter:** A novel, LLM-architecture-specific privacy attack against a component (the MoE router) that production systems expose through APIs or logging more often than people realize, with a measured effect that holds across four different fine-tuning regimes and three architectures — directly useful "what does serving infrastructure leak that you didn't design it to" material for a privacy/membership-inference lesson, and the course currently has no MoE-specific or router-telemetry privacy content at all.
- **Evidence of adoption:** None stated (preprint, 3 days old); not a vendor claim.
- **Major organizations using it:** n/a (attacks a widely-used architecture pattern, not one vendor's product).
- **Open-source implementation:** not stated/confirmed on the abstract page — check the full PDF.
- **Paper:** https://arxiv.org/abs/2610.10616
- **Code:** none confirmed
- **Relationship to existing course material:** `lookup "mixture of experts membership inference"` and `lookup "router telemetry"` found no existing registry/course match — new sub-topic. Sibling to the course's general membership-inference/extraction material but specific to a serving-infrastructure side channel not previously covered.
- **Potential course lesson:** Possible module extension on LLM privacy/extraction: implement a toy MoE model from scratch, show the router-telemetry side channel concretely (train shadow models, measure TPR@low-FPR with vs without routing features), then implement and measure the telemetry-perturbation mitigation's utility cost.
- **Confidence:** medium (clear, consistent effect across 9 controlled settings and 4 training regimes, but single preprint, 3 days old, no independent replication, no code confirmed, and the reported effect sizes — single-digit percentage-point TPR gains — are real but not dramatic).
- **Recommendation:** review for ADD as a new privacy/extraction sub-topic (MoE router telemetry); confirm architecture/domain names and check for code release from the full PDF first.

### C-20261010-02 · Skill Constellations: first dated supply-chain map of 2.19M agent-"Skill" copies on GitHub — stars don't predict risk, fixes rarely propagate, and model-ranked audit targeting beats star-ranked by 14.9% vs 0.5% — new evidence for the deferred "Skills as a trust boundary" topic

- **Class:** B
- **Date discovered:** 2026-10-10
- **Date published:** 2026-10-08 (v1)
- **Source:** https://arxiv.org/abs/2610.11169
- **Organization/researchers:** Fahd Seddik (sole author; affiliation not stated on the abstract page).
- **Category:** agent-security (sub-topic: installable agent "Skills" supply chain)
- **What changed:** The course's registry already tracks "Agent Skills as a trust boundary" (`research/deferred/skill-trust-boundary.md`, status WAIT) via five attack/defense papers (TrustProbe, CoordPoison, Pretext, APEX, and yesterday's PyCache Trap). This paper is a different kind of evidence for the same topic: not a new attack, but the first large-scale empirical measurement of how agent Skills actually propagate across GitHub, i.e. how real and how big this "supply chain without a registry, versions, or provenance" (the author's framing) actually is.
- **Technical summary:** The author builds the first dated copy network of agent Skills by mining the git history of every `SKILL.md` file in a dataset called GitSkills, covering 2,193,119 skill adoptions on GitHub. Findings: a small number of source repositories account for almost all copies; GitHub star counts do not identify which repositories are the true sources being copied from; and copies rarely receive fixes that were later made at the source (i.e. a vulnerability fixed upstream typically stays live in downstream copies). The author fits a ranking model to prioritize which repositories to audit, and reports that auditing the top 100 model-ranked repositories prevents 14.9% of later adoptions of high-risk skills, versus only 0.5% if the 100 most-starred repositories are audited instead — a large gap showing that the obvious popularity-based triage heuristic is close to useless here.
- **Why it might matter:** Satisfies the daily protocol's dedup rule for "genuinely new evidence for a deferred topic" via scale/adoption evidence rather than a new attack mechanism: it quantifies, for the first time, how large and how unpatched the Skills supply chain already is (2.19M adoptions, propagation of unpatched vulnerabilities), which is exactly the kind of "is this still a niche, speculative problem or a real one" evidence the weekly review needs to decide whether `skill-trust-boundary` should finally move off WAIT.
- **Evidence of adoption:** This *is* the adoption evidence (GitHub-scale measurement), not a vendor claim.
- **Major organizations using it:** n/a (measurement study of the open-source GitHub ecosystem, not one vendor's tool).
- **Open-source implementation:** A project website and "interactive viewer" are mentioned; no confirmed public dataset/code repository URL on the abstract page.
- **Paper:** https://arxiv.org/abs/2610.11169
- **Code:** none confirmed
- **Relationship to existing course material:** New evidence for `research/deferred/skill-trust-boundary.md` (same deferred topic; adds ecosystem-scale propagation/audit-prioritization data that the prior five attack/defense papers didn't have). Note: the paper's own text does not cite or reference the prior TrustProbe/CoordPoison/Pretext/APEX/PyCache-Trap line of work — it appears to have been produced independently, which is itself a (soft) form of independent convergence on the same topic being real.
- **Potential course lesson:** If/when the weekly review promotes the Skills-trust-boundary theme to ADD, this paper is the strongest candidate to anchor a "why this matters at scale, and how to triage your own org's imported skills" framing section, paired with PyCache Trap or APEX for the attack/defense mechanics.
- **Confidence:** medium (very large, concrete dataset and a clear, non-obvious audit-prioritization result, but single-author paper, 2 days old, no independent replication, no confirmed public dataset/code, and no bibliography/citation of prior work in this exact theme to cross-check its framing against).
- **Recommendation:** fold into the existing `skill-trust-boundary` deferred file at the next weekly review as adoption/scale evidence (distinct from, and complementary to, C-20261009-03's PyCache Trap attack+defense evidence); do not open a new topic file.

### C-20261010-03 · ProxyEraseAgent: blind single-image watermark removal reaches 94.8% ASR across 11 watermarking systems using only public decoders as proxy oracles — no existing course coverage of AI-content watermarking at all

- **Class:** B
- **Date discovered:** 2026-10-10
- **Date published:** 2026-10-08 (v1)
- **Source:** https://arxiv.org/abs/2610.11290
- **Organization/researchers:** Jun Yao, Chao Wang, Yupeng Qiu, Zehua Ma, Weiming Zhang, Bin Liu, Han Fang (affiliation not stated on the abstract page; not independently re-verified this run).
- **Category:** other (AI-content provenance/watermarking attack; closest listed defense category the protocol names is "provenance & signing")
- **What changed:** AI-generated-content watermarking (the mechanism behind things like SynthID-style image/text provenance marks) is a defense the protocol explicitly lists under "provenance & signing," but the course and registry currently have zero coverage of watermarking in either direction (attack or defense) — `lookup "watermark"` returns no matches at all. This paper is a concrete, measured blind-removal attack against that defense class.
- **Technical summary:** ProxyEraseAgent removes invisible image watermarks from a single watermarked image without access to the real detector, decoder, or any paired clean/watermarked image (the realistic "blind, in the wild" setting, as opposed to prior attacks that assume detector-output access). It ranks publicly available third-party watermark decoders by their calibrated response to the query image, uses the top-ranked ones as proxy decision-boundary estimators, and runs a progressive search over removal operations (geometric distortion, JPEG compression, image reconstruction, gradient perturbation) under a perceptual-quality constraint, guided by the proxy decoders' feedback. Reported result: 94.8% attack success rate across 11 different watermarking systems.
- **Why it might matter:** A measured, realistic-threat-model attack (no insider access needed, just public decoders) against an entire undefended-in-this-course topic area, with a large evaluation (11 systems) — directly useful as the attack half of a future provenance/watermarking lesson. A same-week, closely related design paper, "Could LLM Watermark Detection Be Public?" (https://arxiv.org/abs/2610.12106, submitted 2026-10-08), proposes a split-key scheme to let detectors be released publicly while keeping forgery-detection capability private — noted here as defense-side context (no quantitative results stated), not recorded as its own candidate since it has no measured numbers to evaluate.
- **Evidence of adoption:** None stated (preprint, 2 days old); not a vendor claim.
- **Major organizations using it:** none stated (attacks third-party watermarking systems generically).
- **Open-source implementation:** not stated/confirmed on the abstract page — only third-party code-finder links, no author repository.
- **Paper:** https://arxiv.org/abs/2610.11290
- **Code:** none confirmed
- **Relationship to existing course material:** `lookup "watermark"` and `lookup "LLM text watermarking"` found no existing registry/course match whatsoever — genuinely new topic area for the course, not an extension of an existing lesson.
- **Potential course lesson:** Possible new lesson/lab on AI-content provenance: implement a simple from-scratch image or text watermarking scheme, measure its robustness, then implement a simplified proxy-decoder-guided removal attack and measure the ASR/quality trade-off — pairing naturally with the split-key public-detection design as the defense side.
- **Confidence:** medium (concrete 94.8%/11-systems number, but single preprint, 2 days old, no independent replication, code availability unconfirmed, and this would be an entirely new course topic rather than an extension).
- **Recommendation:** monitor as the opening evidence for a possible new "AI-content provenance/watermarking" topic file; re-review once the full PDF and any code release are checked, and watch for the public-detection design paper's eventual empirical follow-up.
